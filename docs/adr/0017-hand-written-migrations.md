# 0017. Hand-written migrations, with triggers and least-privilege grants

**Status:** accepted

## Context

The schema carries rules that an ORM model cannot express: constraint triggers, append-only
triggers, partial unique indexes, `UNIQUE NULLS NOT DISTINCT`, column-level `UPDATE`
grants, revoked privileges. Autogenerated migrations produce tables and indexes from
models and know nothing of the rest. A schema where part is generated and part is added by
hand is hard to review.

## Decision

- Every Alembic revision is written by hand as SQL, one statement per `op.execute`, one
  revision per module, with a real `downgrade`.
- The migration is the authoritative definition. The SQLAlchemy models mirror it, and a
  test compares the migrated schema with the models and fails on drift. Another test runs
  every migration down and up again.
- Migrations run as the role that owns the schema. The application connects as a second
  role. The baseline grants that role row access by default, and each revision takes away
  what the application must not do: no `UPDATE` or `DELETE` on append-only tables, and
  `UPDATE` on named columns only where a row changes after it is written.
- No column has a default. The application supplies every value.
- Migrations run as a separate step before a deploy, never at application start.

## Consequences

- The whole schema, including triggers and grants, is in one place and reads as SQL.
- If SQL injection ever appeared, it could not rewrite history, change who a withdrawal
  pays, or move an agent to another owner: the role has no privilege to.
- Writing a migration is more work, and the model must be kept in step by hand. The drift
  test catches a mismatch.
- A new table gets full row access for the application until its revision says otherwise.
  The grants test lists what each table allows.
- A new column that the application updates needs a grant as well as a column.
